# 连接可靠性排查

> **2026-11-21 结论修正（重要）**
>
> 本文同日上午的版本把根因归为「Router 只有 20 秒前台窗口，窗口过了就绑不上」。
> 那是**现象**，不是根因。下午又跑了四轮车机实测，从落盘日志定位到真因：
> **应用抢在库唤醒 Router 之前自己建 `SdlManager`，5~11ms 就自毁**。
>
> 修复提交 `fcbef0a`。旧的错误结论保留在文末「附录」，只作为日志数据存档，
> **不要再按它下判断**。

## 一、根因

同一个 `ACL_CONNECTED` 广播，被**两个 receiver** 抢着处理，一个异步、一个同步：

| 谁 | 做什么 | 耗时 |
|---|---|---|
| SDL 库（`SdlBroadcastReceiver.onReceive`） | `SdlDeviceListener` → `ServiceFinder` → `startRouterService()`（异步） | **~110ms** |
| 我们（`BootReceiver`，4.x 遗留） | `startForegroundService(SdlService)` → `onCreate` → `SdlManager.start()`（同步） | **5~20ms** |

我们每次都先到，于是 `SdlManager` 在 Router 还没 listen 的时候就去 bind，
干净利落 `onDestroy`（**连 `onError` 都不打**）→ `handleConnectionClosed()`
→ `stopSelf()`。

车机那边看到的是「有这个 app，但注册一直不完成」，于是卡在「正在连接」，
**等满 2 分钟**才超时退回 AppLink 主界面。

> 注意：`stopSelf` 本身没错（官方语义），错的是**在不该建连接的时候建了**。

## 三、为什么 4.x 时代这套代码能用

不是「我们当年写错了」，是**迁移时漏改**：

| | 4.12.2（`legacy/sdl4` 分支） | 5.8.0 |
|---|---|---|
| `BootReceiver` / `SdlReceiver` / manifest | **一字不差，原样存在** | 同左 |
| 应用层入口 | `SdlProxyALM` + `SdlProxyBuilder` | `SdlManager` |
| 有没有 `SdlManager` 类 | **没有**（`javap` 查过，类不存在） | 有 |
| transport 归属 | `MultiplexTransportConfig.setAppService(this)`，proxy 攥着 Service，后台线程驱动，**能等 Router** | `start()` 一次性动作，Router 不在就 `onDestroy` |

所以同一套广播代码在 4.x 是「必要的变通」，到 5.x 变成「抢跑冲突」。

**最坑的一点**：`BootReceiver` 里那句注释一直写着「这里只保证进程活着」——
那是 4.x 的语义。在 5.x 里 `startForegroundService(SdlService)` 的实际效果是
**立刻建一条连接**，跟「保活」毫无关系。注释和效果在迁移时就脱节了。

## 五、第二轮修复：`queryForConnectedService` 在广播里会崩（2026-11-21 18:3x）

第一轮（第四节）修完之后，**首次连接正常**，但**第二次上车闪退**。

### 5.1 崩溃堆栈

```text
FATAL EXCEPTION: main
java.lang.RuntimeException: Error receiving broadcast
  Intent { act=com.xigaigai.syncglance.ServiceFinder } in ServiceFinder$2
Caused by: android.content.ReceiverCallNotAllowedException:
  BroadcastReceiver components are not allowed to bind to services
    at ReceiverRestrictedContext.bindService
    at SdlRouterStatusProvider.bindToService
    at SdlRouterStatusProvider.checkIsConnected
    at SdlBroadcastReceiver$6.onListObtained
    at RouterServiceValidator.createTrustedListRequest
    at SdlBroadcastReceiver.requestTransportStatus
    at SdlBroadcastReceiver$4.onComplete        ← queryForConnectedService 的回调
    at ServiceFinder.onFinished
```

### 5.2 根因：传错了 context

`queryForConnectedService(context)` 会把**调用方传进来的那个 context**
一路传下去，最后 `RouterServiceValidator` 拿它去 `bindService`：

| 传谁的 context | 结果 |
|---|---|
| `Application` / `Activity` | ✅ 合法 |
| `BroadcastReceiver` 的 `context`（`ReceiverRestrictedContext`） | 💥 `ReceiverCallNotAllowedException` |

第一轮修完后，我把探测放进了 `BootReceiver`，正好踩中第二种。

### 5.3 为什么「首次不崩、第二次崩」

只有「Router 已经在跑、`ServiceFinder` 找得到它」时才会走到 `bindService` 那一步：

| 时刻 | Router 状态 | 结果 |
|---|---|---|
| 18:29:21 首次上车 | 还没起（23.487 才上线） | 找不到 → 不走 bindService → ✅ |
| 18:31:45 再次上车 | 上次留下的 Router 还在跑 | 找到 → bindService → 💥 pid 14326 |
| 18:33:12 又一次 | 同上 | 💥 pid 15098 |

两次崩溃都发生在 `ACL_CONNECTED` 后 **33~50ms**，之后 1.4 秒才出现
`[Boot] 应用启动`（进程被杀后重启）。
用户侧看到的就是：**车机通知显示 connected（Router 活着并已连上车机），
但手机上的 SyncPlay 闪退了**。

### 5.4 修复

| 文件 | 改动 |
|---|---|
| `receiver/BootReceiver.java` | 四个事件**全部不再探测**，只保留日志与白名单判断 |
| `util/Log2.java` | `e(tag,msg,Throwable)` 现在连**堆栈**一起落盘（以前只写 `getMessage()`，而这次 `getMessage()` 是 `null`，等于什么都没记） |
| `SyncGlanceApp.java` | 装 `UncaughtExceptionHandler`：崩前写日志 + `flushNow()` + 堆栈，然后**照常崩**（不掩盖） |
| `service/SdlService.java` | `handleConnectionClosed` 打印「建连至今 ms / RouterAlive / 代际」，用于定位第 7 节那个未解问题 |

探测仍由 `SyncGlanceApp.onCreate` 与 `MainActivity.onCreate` 负责 ——
那两处是 Application / Activity 的 context，安全。

> 这是 **SDL 5.8.0 的设计缺陷**（不该拿调用方的 context 去 `bindService`），
> 但触发条件在我们的用法上，所以由我们规避：**永远不要在 BroadcastReceiver 里
> 调 `queryForConnectedService`。**

修复后，一次正常连接应该按这个顺序出现（`syncplay.log`）：

```text
① [Boot] 收到: android.bluetooth.device.action.ACL_CONNECTED
② [SdlReceiver] ★ onSdlEnabled               ← 车机已连通 Router（只由库触发）
③ [SyncPlay] SyncPlay 服务创建
④ ← {"response":{"name":"RegisterAppInterface" ... "resultCode":"SUCCESS"
⑤ Show / AddCommand / SubscribeButton ← SUCCESS（进 FULL）
```

> `[SdlReceiver] 已调用 queryForConnectedService` **只应该在进程冷启动时**出现
> （来自 `SyncGlanceApp.onCreate` / `MainActivity.onCreate`）。
> **它不该紧跟在 `ACL_CONNECTED` 后面** —— 紧跟就说明 `BootReceiver` 又在探测了，
> 而那条路会在车机已连 Router 时**直接闪退**（见第五节）。

**必须消失的三个现象**：

1. `[Crash] 未捕获异常` —— 这是新加的崩溃日志 TAG，出现即表示又崩了
2. `[SyncPlay] 连接结束（原状态 CONNECTING）`，且与上一条 `服务创建` 间隔 < 1 秒
3. 任何 `ReceiverCallNotAllowedException` / `are not allowed to bind to services`

| 断点 | 含义 |
|---|---|
| ① 之后没有 ② | Router 没被唤醒 → 见第七节（debug 包验证器） |
| ② 之后没有 ③ | 服务启动失败 |
| ③ 之后没有 ④ | 传输层通了但 RAI 没回 |

## 七、已知风险：debug 包的 `IntegrationValidator`

`SdlBroadcastReceiver.onReceive` 里的顺序是：设置 `localRouterClass` → 若 debug 包
就跑 `IntegrationValidator` → 校验失败直接 `athrow`，**整个 `onReceive` 中断**。

本机实测（安装后第一次启动）：

```
[SdlReceiver] queryForConnectedService 失败: RuntimeException
✕ This application has not specified its SDL Receiver properly.
```

第二次进程启动就正常了。也就是说：**每次 `install -r` 之后第一次连车机，
库的 Router 唤醒可能被这一步挡掉。**

以前这个缺口被我们自己那个 `SdlManager` 顺手兜住了（`TransportManager` →
`RouterServiceValidator.wakeUpRouterServices()` 也会起 Router），现在没有兜底。

两条对策：

1. **先上车试**，如果 ③（Router 上线）一直不出现，就在 `BootReceiver` 里补一次
   `SdlReceiver.wakeRouter(context)`（只叫醒 Router、不建连接，等价于被挡掉的那一下）
2. 或者干脆在车上用 release 包（`isDebugMode` 为 false 时不跑验证器）

> ⚠ 不要为了消掉那个 `✕` 去改 manifest。`cmd package query-receivers
> -a sdl.router.startservice` 已确认我们的 receiver 是 `enabled=true exported=true`，
> 声明是正确的，这条是库在 debug 模式下的误报（详见 `AGENTS.md` §5.8.2）。

## 十、根因定论：车机重连有 6~7 秒延迟，SDL5 等不起（2026-11-22）

> **⚠ 标题里的「6~7 秒」是 4.x 的全段**（`ACL_CONNECTED` → 车机回话），本节用它做
> 4.x vs 5.x 的对照。**5.x 真正需要覆盖的只有 2~3 秒** —— 因为 5.x 把那段拆成了
> 「等 `onSdlEnabled` 约 4 秒」+「`SdlManager` 启动后 2~3 秒」两段，
> 应用层重试只需要管后者。实测数据见 §11.2 / §11.3（车机回话 1.79~3.10 秒）。
> 重试参数也因此从「2.5s × 4 = 10 秒」收敛到「**2s × 4 = 8 秒**」。

把 main 的完整功能反向迁移到 `legacy/sdl4`（`SdlProxyALM` + 4.x `TransportBroker`）后，
**恢复连接完全正常**。两次实测（app 前台 / app 完全关闭）都成功。

### 10.1 两次重连的完整时间线

| 事件 | 第一次（app 前台） | 第二次（app 完全关闭） |
|---|---|---|
| `ACL_CONNECTED` | 20:13:57.902 | 20:15:23.660 |
| `服务创建`（SdlProxyALM） | +34ms | +26ms |
| `✓ proxy 建立`（build 返回） | +58ms | +54ms |
| **车机回话 `OnPermissionsChange`** | **+7.36 秒** | **+6.47 秒** |
| `OnHMIStatus` NONE→FULL | 460ms 内 | 928ms 内 |
| `RegisterAppInterface` | `SUCCESS` | `SUCCESS` |

### 10.2 决定性证据：SDL4 **没有走 Router**

这次日志里：

```
RouterService 上线：0 次          ← SyncRouterService 从未被启动
onSdlEnabled：0 次                ← SdlReceiver 从未被回调
```

连接是 `BootReceiver` 在 `ACL_CONNECTED` 时直接 `startForegroundService(SdlService)`，
然后 `SdlProxyALM` 的 `TransportBroker` 因为 `MultiplexTransportConfig.service == null`
（没 setService），**自己开 RFCOMM 监听**（等价于 AppLinkPro 的行为），
**根本没经过 Router 进程**。

### 10.3 车机侧的行为

**车机在蓝牙 ACL 建立后，不是立刻发起 SDL 连接，而是有 6~7 秒的延迟。**

- 这 6~7 秒里，车机在做蓝牙协议栈初始化 + SDP 服务发现
- 延迟结束后才发起 RFCOMM，然后**几百毫秒内**完成 NONE→BACKGROUND→LIMITED→FULL 的
  HMI 序列 + RAI

### 10.4 根因定论（4.x vs 5.x 的本质差异）

| | 4.x（SdlProxyALM + TransportBroker） | 5.x（SdlManager + TransportManager） |
|---|---|---|
| 建连后行为 | `config.service==null` 时**自己开 RFCOMM**（fallback），后台线程**持续等待** | 只 `consumeQueuedRouterService()`，队列空**立即 onDestroy** |
| 面对车机 6~7 秒延迟 | **等得住**（无超时） | **等不起**（5ms 就放弃） |
| 结果 | 等到车机来连，成功 | 车机还没来连就秒退，失败 |

**一句话**：**5.x 移除了「自己开 RFCOMM」的 fallback，强制走 Router；而这台车机
（SYNC 1.1）重连有 6~7 秒延迟，5.x 的 TransportManager 不等待，于是必然失败。
4.x 的 fallback 让应用自己开 RFCOMM 并一直等，天然兼容车机的延迟。**

这也纠正了之前的两个误判：
- 「SDL4 反向迁移版在用 Router」—— 错，日志证明它没走 Router（上线 0 次）
- 「AppLinkPro 借用了我们的 Router」—— 错，实验证明它被包可见性 BLOCKED，自己开 RFCOMM

### 10.5 对 SDL5 的启示

SDL5 要解决恢复连接，可选方向：

1. **受控重试**（已加 `1af2f72`，参数后经 `b2797fd` 定为 **2s × 4 = 8 秒**）：
   秒失败时延迟重试。**注意「6~7 秒」是 4.x 全段**；5.x 真正需要覆盖的是
   `SdlManager` 启动后到车机回话那 **2~3 秒**（实测见 §11.2/§11.3）
2. **onSdlEnabled 先 wakeRouter**（已加）：确保 Router 前台
3. **让 Router 窗口 ≥ 车机延迟**：本车需要 Router 在 `ACL_CONNECTED` 后保持可被发现
   至少 7 秒（当前 10~20 秒，理论够，但要看 Router 何时真正开始监听）
4. **最彻底**：像 4.x 那样，让 5.x 在 Router 不可用时也能 fallback 自己开 RFCOMM
   —— 但这需要改库，不现实；受控重试是应用层能做到的最接近方案

> **2026-11-22 已验证**：受控重试生效。实测 SDL5 恢复连接 4 次里只 1 次秒失败，
> 且重试 1 次（2.5 秒后）就成功。SdlManager 阶段的车机回话延迟是 2~3 秒，
> 不是之前 SDL4 对照组看到的 6~7 秒「全段」（5.x 把那段拆成了「等 onSdlEnabled 约 4 秒」
> +「SdlManager 后 2~3 秒」两段）。重试窗口最终定为 8 秒（2s × 4），
> 按福特 SYNC 1.1 / 2012 福克斯 MFD4 车机蓝牙栈冷启动偏慢的响应速度，密集采样并留余量。

## 十一、移除前台通知后的复测（2026-11-22 21:1x）

> 背景：当天把 `SdlService` 的前台通知整条移除，`SdlReceiver` 改用 `startService`
> （见 `docs/通知移除与存活权衡.md`）。本文记录复测数据 + 两条被**修正**的结论。

### 11.1 修正一：真正的唤醒卡口是 `ACL_CONNECTED`，不是 `onSdlEnabled`

21:17:02.900  ★ onSdlEnabled                    ← Router 连上车机后才发（+38.3s）

| 轮次 | ACL_CONNECTED | Router 上线 | onSdlEnabled | ACL→onSdlEnabled |
|---|---|---|---|---|
| 1 | 21:16:24.595 | 21:16:27.306 | 21:17:02.900 | 38.3s（Router 冷启 + 车机发现） |

### 11.5 谁负责启动 Router —— 两个 receiver 的分工（2026-11-22 澄清）

常见误解：「Router 自己监听 ACL_CONNECTED」。**不是** ——
`SdlRouterService` 是 **Service 不是 receiver**，它没法监听广播，只能被别人启动。

反编译 `sdl_android 5.8.0` 确认的完整链路：

```
车机蓝牙连上
  → 系统发 ACL_CONNECTED
  → 命中 SdlReceiver 的 intent-filter（它继承库的 SdlBroadcastReceiver）
  → 系统拉起应用进程
  → 库的 SdlBroadcastReceiver.onReceive()      ← 整个库里唯一匹配该 action 的类
  → wakeUpRouterService()
  → Context.startForegroundService(RouterService)   ← Router 这才起来（也是那条 SDL 通知的来源）
```

本项目的两个 receiver 分工：

| receiver | 声明 `ACL_CONNECTED` | 实际动作 |
|---|---|---|
| `SdlReceiver`（继承库的 `SdlBroadcastReceiver`） | ✅ | **真正拉起 Router**（库代码）+ 车机连通后 `onSdlEnabled` → 拉起 `SdlService` |
| `BootReceiver`（4.x 时代自写的） | ✅ | **一个 start 都不调**，只记日志 + 维护 MAC 白名单 |

→ 所以 `BootReceiver` 的 `ACL_CONNECTED` 监听对「拉起」是**冗余**的，删掉不影响连接；
留着是因为它是唯一记录「谁把进程叫醒」的地方（`SdlReceiver` 要等车机连通 Router 后
才打 `onSdlEnabled`，中间那段没人记），而且零成本。

**日志措辞（2026-11-22 起）**：`BootReceiver` 不再打「【启动来源】」（那个词会让人
误以为是它发起了连接），改成按「进程是不是刚被这条广播拉起」区分：

```
[Boot] 【进程被拉起】蓝牙 ACL_CONNECTED ← SYNC / <MAC>      ← Application.onCreate 后 1.5s 内
[Boot] 【进程已运行】收到 蓝牙 ACL_CONNECTED ← SYNC / <MAC>  ← 进程早就活着
[Boot] 【事件】蓝牙已开启                                    ← STATE_CHANGED，不是"来源"
```

判据：`SystemClock.elapsedRealtime() - SyncGlanceApp.processStartAtMs() < 1500ms`。
这条区分直接回答了 §11.4 里「进程到底是被谁重新拉起的」那种问题。

## 十二、「忽然断联」的两种新故障（2026-11-24）

> 现象：正常使用中突然断连，之后 Router 起不来、车机点「查找软件」找不到应用。
> 查下来是**两个独立问题叠加**，且都不在 SDL 代码层面。

### 12.1 关键辨别：日志里有没有「连接结束」

| 日志表现 | 含义 |
|---|---|
| 有 `连接结束（原状态 …）` + `服务销毁` | 正常断链，`SdlManagerListener.onDestroy` 走到了 |
| **两者都没有，后面却出现 `应用启动`** | **进程被杀了** —— 系统强杀不会给回调机会 |

判断依据：断开前最后一次 `应用启动` 的时间点是否落在「本不该退出」的时刻。

### 12.2 根因 A：被 ROM 杀进程（Motorola DeviceGuard）

```text
11-24 23:22:59.106 I/am_kill: [0,30459,com.xigaigai.syncglance,200,
    stop com.xigaigai.syncglance due to from pid 5782 and uid 10266

```

**主进程和 Router 进程一起被 `com.motorola.deviceguard` 杀掉**，前台服务也照杀。
随后 23:23:00 那个「假 `BOOT_COMPLETED`」又把进程拉起来，但**不会重建 SDL 会话**
（车机蓝牙还连着，SDL 那边已经没人应答）。

查法：

```powershell

```

**当时的加重因素**：本应用**不在电池优化白名单**（`dumpsys deviceidle whitelist` 里没有）。

对策（按有效性）：

1. 电池优化白名单 —— `& $adb shell cmd deviceidle whitelist +com.xigaigai.syncglance`
   （或系统设置里「电池 → 不受限制」）
2. 最近任务卡片里**锁定**本应用
3. ROM 的「自启动 / 后台运行管理」里放行
4. 卸掉其它 SDL 测试应用（见 12.3）

### 12.3 加重因素：手机上并存多个 SDL 应用

当时的列表：`com.smartdevicelink.rpcbuilder`、`jp.co.toyota.sdl.capp.toyota`、
`com.ford.helloapplink`（外加本应用）。

SDL 的多路复用设计会让 Router 连上后**去启动同设备上的其它 SDL 应用**，
日志里能看到：

```text
D/PackageManager: filterSelfStart: callingUid = 10422,
    targetPackage = jp.co.toyota.sdl.capp.toyota, type = 204,
    intent = Intent { act=sdl.router.startservice }
```

两个风险：

1. 触发 ROM 的**「关联启动」限制** —— 这正是 DeviceGuard 一类管家应用的判定依据
2. 多个 `RouterService` 可能**抢 SDP / RFCOMM** 通道

→ 非测试需要就卸掉，只留本应用。

### 12.4 根因 B：蓝牙链路层 LMP 超时（App 无能为力）

`23:25:10 ACL_DISCONNECTED` 之后，系统蓝牙栈每 ~40 秒一次：

```text
W/bt_btm_sec: btm_sec_disconnected: Got uncommon disconnection reason:
    HCI_ERR_LMP_RESPONSE_TIMEOUT handle:0x0004
E/bt_btm_ble: btm_ble_read_remote_features_complete:
    Failed to read remote features status:HCI_ERR_LMP_RESPONSE_TIMEOUT
```

`HCI_ERR_LMP_RESPONSE_TIMEOUT` = **手机发链路层请求，车机不回应**。
当时 `Active Device = null`，A2DP / Headset 全部 `Disconnected`。

因果链：

```
车机蓝牙模块挂死 → ACL 建不起来 → 没有 ACL_CONNECTED 广播
  → Router 不会被拉起（它只由该广播或手动 wake 启动）
  → 车机「查找软件」做 SDP 查询时手机上没人监听 RFCOMM → 找不到应用
```

**App 无法自救** —— 它只在被动等广播。处理办法：

- 车机**熄火再启动**（SYNC 1.1 的蓝牙模块挂死是常见病）
- 手机蓝牙关开一次 / 在设置里手动连接 `SYNC`
- 反复失败就取消配对后重配

查法：

```powershell
& $adb shell "dumpsys bluetooth_manager | grep -E 'curState=|Active Device|mConnectionState'"
& $adb logcat -d -b all | Select-String 'HCI_ERR_LMP_RESPONSE_TIMEOUT'
```
