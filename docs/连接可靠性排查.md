# 连接可靠性排查

> **2026-11-21 结论修正（重要）**
>
> 本文同日上午的版本把根因归为「Router 只有 20 秒前台窗口，窗口过了就绑不上」。
> 那是**现象**，不是根因。下午又跑了四轮车机实测，从落盘日志定位到真因：
> **应用抢在库唤醒 Router 之前自己建 `SdlManager`，5~11ms 就自毁**。
>
> 修复提交 `fcbef0a`。旧的错误结论保留在文末「附录」，只作为日志数据存档，

## 一、根因

同一个 `ACL_CONNECTED` 广播，被**两个 receiver** 抢着处理，一个异步、一个同步：

| 谁 | 做什么 | 耗时 |
|---|---|---|
| SDL 库（`SdlBroadcastReceiver.onReceive`） | `SdlDeviceListener` → `ServiceFinder` → `startRouterService()`（异步） | **~110ms** |
| 我们（`BootReceiver`，4.x 遗留） | `startForegroundService(SdlService)` → `onCreate` → `SdlManager.start()`（同步） | **5~20ms** |

我们每次都先到，于是 `SdlManager` 在 Router 还没 listen 的时候就去 bind，
干净利落 `onDestroy`（**连 `onError` 都不打**）→ `handleConnectionClosed()`
→ `stopSelf()`。

车机那边看到的是「有这个 app，但注册一直不完成」，于是卡在「正在连接」，
**等满 2 分钟**才超时退回 AppLink 主界面。

> 注意：`stopSelf` 本身没错（官方语义），错的是**在不该建连接的时候建了**。

### 2.3 成功的形态（对照组）

```
15:14:18.923  [SdlReceiver] ★ onSdlEnabled
15:14:18.948  [SyncPlay] 服务创建
15:14:19.010  [SyncPlay] ✓ SdlManager 已启动
```

成功和失败的唯一区别就是「建 `SdlManager` 那一刻 Router 在不在」。

### 2.4 假 `BOOT_COMPLETED`：国内 ROM 的保活把进程反复拉活

```
15:14:57.994  [Boot] 收到: android.intent.action.BOOT_COMPLETED
15:15:17.652  [Boot] 收到: android.intent.action.BOOT_COMPLETED
15:15:52.440  [Boot] 收到: android.intent.action.BOOT_COMPLETED
```

而 `adb shell cat /proc/uptime` 显示手机**已经连续运行 6.2 天**，根本没重启。

后来在电脑旁复现：`adb shell am broadcast` 把进程拉起后 **22ms**，系统又补发一条
`BOOT_COMPLETED`。所以它是「进程被拉起时系统补发的假广播」，不是开机。

以前每来一条就建一个收不到任何回应的僵尸 `SdlManager`；现在改成探测之后无害。

### 2.5 那三次「起来了但零响应」——未证实

15:14:58 / 15:15:17 / 15:15:52 三次都打出了
`✓ SdlManager 已启动，等待车机连上并完成注册`，但直到 15:16:19 超时，
**一条 `←` 报文都没有**。

推断：Router 里还挂着 15:14:18 那条会话（车机侧已转到 `NONE`/`LIMITED` 但没断），
新 `SdlManager` 的 RAI 排不进去，车机只认第一条。

**这条没证实** —— 需要 `logcat` 里 `tag: SDL` 的库内部日志，而车里连不上 adb。
好在修复之后这类重启本身就不该再发生。

## 三、为什么 4.x 时代这套代码能用

不是「我们当年写错了」，是**迁移时漏改**：

| | 4.12.2（`legacy/sdl4` 分支） | 5.8.0 |
|---|---|---|
| `BootReceiver` / `SdlReceiver` / manifest | **一字不差，原样存在** | 同左 |
| 应用层入口 | `SdlProxyALM` + `SdlProxyBuilder` | `SdlManager` |
| 有没有 `SdlManager` 类 | **没有**（`javap` 查过，类不存在） | 有 |
| transport 归属 | `MultiplexTransportConfig.setAppService(this)`，proxy 攥着 Service，后台线程驱动，**能等 Router** | `start()` 一次性动作，Router 不在就 `onDestroy` |

所以同一套广播代码在 4.x 是「必要的变通」，到 5.x 变成「抢跑冲突」。

**最坑的一点**：`BootReceiver` 里那句注释一直写着「这里只保证进程活着」——
那是 4.x 的语义。在 5.x 里 `startForegroundService(SdlService)` 的实际效果是
**立刻建一条连接**，跟「保活」毫无关系。注释和效果在迁移时就脱节了。

## 四、修复（`fcbef0a`）

| 文件 | 改动 |
|---|---|
| `receiver/BootReceiver.java` | 四个事件（`BOOT_COMPLETED` / `ACL_CONNECTED` / `STATE_CHANGED(ON)` / `MY_PACKAGE_REPLACED`）一律改为 `queryForConnectedService` 探测 |
| `activity/MainActivity.java` | 删掉 `startSdlService()`，改为同样的探测 |

**保留不动**：`SdlReceiver.onSdlEnabled` 的双路启动（PendingIntent + `startSelf`），
它是唯一被实车证实能成功的入口。

职责划分回到官方：

```
ACL_CONNECTED → 库 SdlBroadcastReceiver.onReceive → wakeUpRouterService()   只起 Router
车机连上 Router → sdl.router.startservice → onSdlEnabled()                这才轮到应用
应用 → startForegroundService(SdlService) → SdlManager.start()
```

修复后，一次正常连接应该按这个顺序出现（`syncplay.log`）：

```text
① [Boot] 收到: android.bluetooth.device.action.ACL_CONNECTED
② [SdlReceiver] 已调用 queryForConnectedService
③ [Router] RouterService 上线                        ← 现在只由库唤醒
```

| 断点 | 含义 |
|---|---|
| ①② 之后没有 ③ | Router 没被唤醒 → 见第六节（debug 包验证器） |
| ③ 之后没有 ④ | 车机没连上 Router（本车需要人工「查找移动应用」） |
| ④ 之后没有 ⑤ | 服务启动失败 |
| ⑤ 之后没有 ⑥ | 传输层通了但 RAI 没回 |

## 六、已知风险：debug 包的 `IntegrationValidator`

`SdlBroadcastReceiver.onReceive` 里的顺序是：设置 `localRouterClass` → 若 debug 包
就跑 `IntegrationValidator` → 校验失败直接 `athrow`，**整个 `onReceive` 中断**。

本机实测（安装后第一次启动）：

```
[SdlReceiver] queryForConnectedService 失败: RuntimeException
✕ This application has not specified its SDL Receiver properly.
```

第二次进程启动就正常了。也就是说：**每次 `install -r` 之后第一次连车机，
库的 Router 唤醒可能被这一步挡掉。**

以前这个缺口被我们自己那个 `SdlManager` 顺手兜住了（`TransportManager` →
`RouterServiceValidator.wakeUpRouterServices()` 也会起 Router），现在没有兜底。

两条对策：

1. **先上车试**，如果 ③（Router 上线）一直不出现，就在 `BootReceiver` 里补一次
   `SdlReceiver.wakeRouter(context)`（只叫醒 Router、不建连接，等价于被挡掉的那一下）
2. 或者干脆在车上用 release 包（`isDebugMode` 为 false 时不跑验证器）

> ⚠ 不要为了消掉那个 `✕` 去改 manifest。`cmd package query-receivers
> -a sdl.router.startservice` 已确认我们的 receiver 是 `enabled=true exported=true`，
> 声明是正确的，这条是库在 debug 模式下的误报（详见 `AGENTS.md` §5.8.2）。
