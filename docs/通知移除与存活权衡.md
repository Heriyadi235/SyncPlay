## 一、背景与决策

### 1.1 现象

车机连接前后，通知栏会出现**两条**本质重复的通知：

| 来源 | 标题 | 正文 | 出现时机 |
|---|---|---|---|
| SDL 库（Router 进程） | `SDL: com.xigaigai.syncglance`（debug 包）/ `SmartDeviceLink`（release 包） | `Waiting for connection...` → 连上后换成已连接文案 | 车机查找应用 / 建立连接期间 |
| 本应用（`SdlService`） | `SyncPlay` | 中文状态枚举（未连接 · 等待车机 / 显示中 …） | `SdlService` 存活期间 |

### 1.2 两个决定

1. **SDL 那条的标题改不了 → 放弃改名。**
   反编译 `sdl_android-5.8.0.aar` 确认标题是**硬编码**在
   `com.smartdevicelink.transport.SdlRouterService.enterForeground(String,long,boolean)` 里：

   ```java
   // 135~204 字节码还原
   if ((getApplicationInfo().flags & ApplicationInfo.FLAG_DEBUGGABLE) != 0) {
       ComponentName cn = new ComponentName(this, getClass());
       builder.setContentTitle("SDL:" + cn.getPackageName());   // debug 包
   } else {
       builder.setContentTitle("SmartDeviceLink");              // release 包
   }
   ```

   `enterForeground` / `safeStartForeground` / `createConnectedNotificationText` **全是 private**，
   库里没有提供任何 hook 或配置项。要做到只能是「等它贴完，再用
   `getActiveNotifications()` 改 `extras` 里的 `EXTRA_TITLE` 重贴同一个 id」这种
   事后覆盖的 hack，而且库每次重贴都得再覆盖一次 —— **已放弃**，见[第十节](#十附录sdl-那条通知的标题为什么改不了)。

2. **本应用的通知直接删掉。**

改动只涉及两个文件。**AndroidManifest 未动**（`SdlService` 上的
`android:foregroundServiceType="connectedDevice"` 保留 —— 一个服务声明了类型但

**未删除**：`com.xigaigai.syncglance.display.ConnectionStatus.java` 整个文件保留。
它目前是死代码（唯一调用者就是 `notificationText()`），但恢复通知时可直接复用。

### 2.2 `app/src/main/java/com/xigaigai/syncglance/receiver/SdlReceiver.java`

| 改动 | 原因 |
|---|---|
| `startSelf()`：`startForegroundService` → **`startService`** | 见[第三节](#三为什么必须连带改-sdlreceiver)，不改会崩 |
| 删除 Android 14+ 的 `AndroidTools.hasForegroundServiceTypePermission` 检查 | 那是「启动 FGS 的前置校验」，已无 FGS |
| 删除 `startViaPendingIntent()` 及其调用 | 库给的 PendingIntent 目标 Intent **只有 `setPackage`、没有 component**，指不到 `SdlService`，实测 `send()` 成功但服务从未创建。机制详见 [`sdl生命周期-场景对照.md`](sdl生命周期-场景对照.md) 注② |
| 删除 `android.app.PendingIntent`、`com.smartdevicelink.util.AndroidTools` import | 上述删除后不再使用 |
| 启动失败改打 **ERROR + 完整堆栈** | 万一被 ROM 拦，日志要能一眼看出来 |

`wakeRouter()` **未改**：它启动的是 RouterService，由库自己调 `enterForeground`，
仍应使用 `startForegroundService`（否则可能触发「5 秒」问题，因为库在这条路径上
确实会进前台）。

### 2.3 `app/src/main/java/com/xigaigai/syncglance/SyncGlanceApp.java`

新增 `removeLegacyNotificationChannel()`，在主进程 `onCreate` 里调一次，
把旧渠道 `syncglance` 删掉。

**为什么**：通知已经不发了，但**通知渠道一旦创建就永久留在系统设置里**，
应用不主动删就永远删不掉 —— 用户会在「设置 → 通知」里看到一个
永远不会有通知的「SyncPlay 连接状态」类别。实测删前
`adb shell dumpsys notification | grep syncglance` 里能看到这条渠道残留。

该方法幂等（渠道不存在时是 no-op），每次启动调一次即可。

## 三、为什么必须连带改 SdlReceiver

`startForegroundService()` 的契约是：**服务必须在 5 秒内调用 `startForeground()`**，
否则系统抛

```
android.app.RemoteServiceException:
  Context.startForegroundService() did not then call Service.startForeground()
```

并**直接杀掉该服务**（表现为 App 崩溃/服务起不来，车机侧卡在「正在连接」直到超时）。

所以「删除通知」不是删一行 `notify()` 就完事 —— 只要还有任何一处用
`startForegroundService(SdlService)` 拉起它，就得同时删掉通知，二者只能同进退。

本项目里拉起 `SdlService` 的地方只有一处：

- `SdlReceiver.onSdlEnabled()` → `startSelf()`（已改）
- `MainActivity` **只调 `pokeIfBluetoothConnected()` / `queryForConnectedService()`**，
  不启动服务（`startSdlService()` 早已删除，见 `MainActivity` 里 132~144 行的注释）
- `BootReceiver` 明确「不启动服务」

## 四、为什么后台启动不会被拦（关键前提）

`startService` 在 Android 8+ 会受「后台应用不能启动服务」限制。这条路径不受限，
有两层保险：

1. **同 uid 有前台服务。** 广播由 Router 进程（`com.smartdevicelink.router`，
   `foregroundServiceType="connectedDevice"`，常驻前台服务）发出。UidRecord 的
   重要性是 **按 uid 聚合**的，只要该 uid 下有进程处于 foreground-service，
   整个 uid 就不受后台启动限制。
2. **Receiver 执行期间在临时白名单。** 即便进程是从零被拉起，接收广播期间
   App 处于临时允许状态，服务启动本身合法。

万一某些 OEM ROM 仍然拦截，会抛 `IllegalStateException: Not allowed to start service ...`。
`startSelf()` 已改为 **ERROR + 完整堆栈**日志，搜索关键字：

```
★ 启动 SdlService 失败
```

## 五、唤醒链路不依赖 SdlService 存活（已反编译验证）

这是本次改动成立的核心前提，**已从 `sdl_android-5.8.0.aar` 字节码确认**：

车机通过 RFCOMM 连上后，Router 进程在 `SdlRouterService` 里构造并发出**明确指向本包的广播**：

```java
Intent intent = new Intent();
intent.setAction("sdl.router.startservice");        // ← 我们 Manifest 里 SdlReceiver 声明了它
intent.putExtra("sdl_enabled", true);
intent.putExtra("force_connect", true);
intent.putExtra("package_name", getPackageName());
intent.putExtra("component_name", new ComponentName(this, getClass()));
intent.addFlags(Intent.FLAG_RECEIVER_FOREGROUND);
if (Build.VERSION.SDK_INT >= 31) {
    PendingIntent pi = PendingIntent.getForegroundService(ctx, reqCode, svc, FLAG_UPDATE_CURRENT|FLAG_IMMUTABLE);
    intent.putExtra("pending_intent", pi);
}
AndroidTools.sendExplicitBroadcast(getApplicationContext(), intent, null);
```

一次完整链路：

```
车机 RFCOMM 连上
  → Router 进程（独立、常驻、前台服务）收到连接
  → 广播 sdl.router.startservice（明确指向本包）
  → 系统拉起我们的主进程（进程被杀了也一样）
  → SdlReceiver.onSdlEnabled()
  → startService(SdlService) → 重建 SdlManager → RAI
```

另有第二条兜底：`ACL_CONNECTED` 广播同时打在 `SdlReceiver` 和 `BootReceiver` 上。

**结论：主进程没活着，车机连上时也一定会被拉起来。** 本次改动失去的是
「进程一直活着」的保证，不是「能被唤醒」的通道。

### 5.1 实车时序：真正的卡口是 `ACL_CONNECTED`，不是 `onSdlEnabled`

2026-11-22 上车实测 4 轮，形态完全一致：

```
21:16:24.595  [Boot] ACL_CONNECTED ← SYNC       ← 进程被这条广播拉起
21:16:27.306  [Router] RouterService 上线        ← Router 这才被唤醒（+2.7s）
21:17:02.900  [SdlReceiver] ★ onSdlEnabled      ← Router 连上车机后才发（+38.3s）
```

| 轮次 | ACL_CONNECTED | Router 上线 | onSdlEnabled | ACL→onSdlEnabled |
|---|---|---|---|---|
| 1 | 21:16:24.595 | 21:16:27.306 | 21:17:02.900 | 38.3s（Router 冷启） |
| 2 | 21:17:37.446 | 21:17:37.476 | 21:17:40.810 | 3.36s |
| 3 | 21:18:03.026 | 21:18:05.496 | 21:18:06.648 | 3.62s |
| 4 | 21:20:54.607 | 21:20:54.651 | 21:20:57.205 | 2.60s |

→ **「进程冷」的时刻在 `ACL_CONNECTED`，不在 `onSdlEnabled`。**
那条由 manifest receiver 承担，系统一定会拉起进程，
和「后台能不能 `startService`」是两件事。

### 5.2 结构性保证：`startService` 不会在「无前台服务」的 uid 上执行

`sdl.router.startservice` **是 Router 自己发出**的，所以 `onSdlEnabled` 到达时
Router 必然已经在跑 —— 而 Router 是同一 uid 下的前台服务
（`foregroundServiceType="connectedDevice"`）。上表 4 轮全部满足
「Router 上线时间 < onSdlEnabled」，这是时序必然，不是运气。

**推论：本次改动引入的「后台启动服务被拦」风险在结构上 ≈ 0。**
即使主进程在两轮之间被杀，Router 进程仍在，uid 仍处于
foreground-service 状态，`startService` 依旧合法。
`SdlReceiver.startSelf()` 里那条 ERROR 日志只是保险。

## 六、放弃掉的东西 / 新增的风险

| 项 | 改之前（前台服务） | 改之后（普通服务） |
|---|---|---|
| 通知栏 | 常驻一条中文状态 | 无 |
| 进程优先级 | foreground-service（几乎不会被 LMK 回收） | service（比 cached 好，但可回收） |
| 后台存活 | 无时间限制 | **进入空置后约几分钟可能被系统停掉**（Android 8+ Background Execution Limits） |
| 断开后行为 | `stopSelf()`（不变） | 同 |
| 幂等/重建 | `START_STICKY` | 同（进程被杀后系统会择机重启服务） |

**实际影响面**：`SdlService` 的存活窗口本来就是「车机连接期间」——
连上才建会话，断开就 `stopSelf()`。所以风险集中在
**「已连上车机、正在跑会话，但 App 界面在后台」的这段时间**：
若此时被系统判定空置并停掉服务，会话会中断（车机侧掉线）。

此外，`SdlService` 里那套 2s × 4 = 8 秒的「秒失败重试」只在服务活着时才跑，
被停掉之后就不会再触发。

### 6.1 首轮实车验证（2026-11-22 21:1x）：没观察到任何代价

用户在车上实测了「清后台 / 不清后台」两种状态，共 5 次连接（其中 4 次真实建会话），
与改动前的同一版 SDL5（`run_sdl5.log`，通知还在）逐段对比：

| 指标 | 改后 | 改前 | 判定 |
|---|---|---|---|
| 进程/服务启动（onSdlEnabled→服务创建） | 15 / 16 / 21 / 32 ms | 16 / 19 / 24 / 80 ms | 改后更快 |
| 建 SdlManager | 58 / 91 ms | 48ms（另两次 437/648ms 是首次类加载） | 持平 |
| 车机回话（未重试） | 3.05 / 3.10 s | 2.00 / 2.90 / 2.63 s | 慢 0.2~1.0s，噪声内 |
| 车机回话（重试后） | 1.79 / 2.32 s | 2.15 s | 持平 |
| 秒失败后重试 | 2 次，均 1/4 成功 | 1 次，1/4 成功 | 8 秒窗口从未用完 |

**→ 移除通知没有让响应变慢，也没有让连接变差。**

另外两条本次核实/修正的结论：

1. **唤醒卡口是 `ACL_CONNECTED`，且 `startService` 永远不会在同 uid 没有前台服务时
   执行**（Router 必须先存在才能发那条广播）→ 后台启动被拦的风险 ≈ 0，见 5.1 / 5.2。
2. **「进程重启偏多」不是被 LMK 回收**：`uptime` 4:58、`system_server`/`zygote`
   全程未重启，三次进程启动都是被**假 `BOOT_COMPLETED`** 拉起的
   （`docs/连接可靠性排查.md` §2.4 已记录过的现象）。见该文档 §11.4。

> 完整数据（分段耗时表、基线对照、重试统计）见
> [`docs/连接可靠性排查.md`](连接可靠性排查.md) 第十一节。

唯一仍未覆盖的场景：**熄火 30~60 分钟后**再上车、以及**手机后台放置超过 10 分钟**
之后的服务存活 —— 这两档需要更长时间观察，见 7.4。

## 七、电池白名单 / 锁定后台有用吗？

**有用，而且能补掉一部分风险，但不是「等价替代前台服务」。**

### 7.1 「不优化电池用量」白名单（AOSP 层）

系统设置 → 应用 → SyncGlance → 电池 → **不受限制 / 允许后台活动**
（对应 `adb shell dumpsys deviceidle whitelist`，或
`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）。

作用：把 App 放进 **power save whitelist**。白名单 App 不会进入 Doze 的深度限制，
也**不会被判为 idle** —— 而 Android 8+ 「空置后停掉后台服务」正是以 idle 为前提的。
所以在 AOSP 语义下，白名单**确实能显著延长普通后台服务的存活时间**。

局限：这是「不要因为省电而限制我」，不是「我有前台服务」。个别 ROM 仍可能
在极端内存压力下回收，且不改变「没有前台服务」这一事实。

### 7.2 OEM 的「锁定后台 / 允许后台运行」

国产 ROM（MIUI/HyperOS、ColorOS、OriginOS、MagicOS、EMUI…）另有**自家进程清理器**，
它不走 AOSP 那套逻辑，也是最常见的真凶。对应开关大致是：

- 最近任务卡片**下拉/长按 → 锁定**（加锁后不被一键清理）
- 设置 → 应用 → **自启动 / 允许后台活动 / 关联启动**
- 电池 → **应用耗电管理 → 允许完全后台行为**（各家叫法不同）

作用：直接免除 ROM 层的杀进程。**优先级比 7.1 更高** —— 如果只做一个，做这个。

### 7.3 二者叠加的实际效果

| 措施 | 覆盖的系统层 |
|---|---|
| 不优化电池用量 | AOSP Doze / App Standby / idle 判定 |
| 锁定后台 + 自启动 | OEM 清理器、后台限制白名单 |

两条都开，普通后台服务在多数机器上能活很久，**大致接近**前台服务的存活表现
（差别主要在于：没有前台服务时，系统仍可能因内存压力优先回收；而前台服务是
"最后才回收"的优先级）。

**但它们都不能替代一件事**：`startForegroundService` 的 5 秒契约。
本次已经改用 `startService`，所以那条已不适用。

### 7.4 建议的验收方式

首轮（短时、多轮重连）已通过，见 6.1。剩下的只有长时段观察：

- **停车熄火 30~60 分钟后再上车**，车机能否连上；
- **手机放后台超过 10 分钟**，`SdlService` 是否还活着（日志里有无「服务销毁」）。

注意：清后台 / 不清后台两种状态首轮都测过，都稳定。
若长时间档位出现掉线，再加白名单复测；仍不行就回退前台通知。

### 8.4 唤起链路（关掉 App 进程后）

```
adb shell am force-stop com.xigaigai.syncglance
```

然后上车/让车机查找应用。日志应依次出现：

```
[SdlReceiver] ★ onSdlEnabled —— 车机已连通 RouterService，启动 SdlService
[SdlReceiver] 已直接启动 SdlService（startService，非前台）
[SyncPlay] SyncPlay 服务创建（连接层）
```

**如果没有出现** `★ 启动 SdlService 失败` 而链路正常，说明后台启动未被拦。

> 优先级说明（2026-11-22 修正）：这项**不是**最关键的验证。
> 按 5.2 的时序分析，`onSdlEnabled` 到达时 Router 必然已在跑且是前台服务，
> 所以这条路径在结构上不会被拦。真正值得花时间验的是 7.4 的两个长时段档位。
> 但作为一次性确认，跑一次仍然值得。

### 8.5 关键日志关键字（出问题时搜这些）

| 关键字 | 含义 |
|---|---|
| `★ 启动 SdlService 失败` | 后台服务启动被拦，**该回退方案了** |
| `Not allowed to start service` | 同上（`IllegalStateException` 原文） |
| `did not then call Service.startForeground` | 还有地方在用 `startForegroundService`（漏改） |
| `服务销毁（连接层退出` | 服务退出；若发生在「本不该退出」的时刻，说明被系统停了 |

    private void createChannel() {
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
            NotificationChannel ch = new NotificationChannel(
                    CHANNEL_ID, "SyncPlay 连接状态", NotificationManager.IMPORTANCE_LOW);

    private Notification buildNotification() {
        Notification.Builder b = (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O)

                : new Notification.Builder(this);

        b.setContentTitle(APP_NAME)

                      | android.app.PendingIntent.FLAG_IMMUTABLE
                    : android.app.PendingIntent.FLAG_UPDATE_CURRENT;
            b.setContentIntent(android.app.PendingIntent.getActivity(this, 0, i, flags));
        } catch (Exception ignored) { }

        return b.build();
    }

    private String notificationText() {
        return com.xigaigai.syncglance.display.ConnectionStatus.text(
                lifecycle == null ? null : lifecycle.getState(),
                routerAlive,
                closedOnce,
                renderer == null ? null : renderer.currentState());
    }

    private String lastNotifText;

    public void updateNotification() {
        try {
            String text = notificationText();
            if (text.equals(lastNotifText)) return;
            lastNotifText = text;

            NotificationManager nm = getSystemService(NotificationManager.class);
            if (nm != null) {
                if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
                    NotificationChannel ch = nm.getNotificationChannel(CHANNEL_ID);
                    if (ch != null && ch.getImportance() == NotificationManager.IMPORTANCE_NONE) {
                        if (!warnedNoNotif) {
                            warnedNoNotif = true;
                            Log2.w(TAG, "⚠ 通知已被关闭，前台保活能力下降。"
                                    + "请在系统设置里为 SyncPlay 重新开启通知");
                        }
                        return;
                    }
                }
                nm.notify(NOTIF_ID, buildNotification());
            }
        } catch (Exception e) {
            Log2.w(TAG, "刷新通知失败: " + e.getMessage());
        }
    }

    private boolean warnedNoNotif = false;

## 十、附录：SDL 那条通知的标题为什么改不了

留档，避免以后重复研究。

**结论**：库里没有暴露点，只能事后覆盖，已放弃。

1. 通知由 `com.smartdevicelink.transport.SdlRouterService` 发出（`FOREGROUND_SERVICE_ID`
   与渠道 `sdl_notification_channel`）。
2. 标题逻辑在 `enterForeground(String, long, boolean)` 里**硬编码**：
   - app 是 **debuggable** → `"SDL:" + 包名`
   - app **不是** debuggable（release）→ `"SmartDeviceLink"`
   - → **两种都是写死的，release 包也不会显示应用名。**
3. `enterForeground` / `safeStartForeground` / `createConnectedNotificationText`
   **全部 private**，不可覆写；`TransportConstants` 里也没有「自定义标题」之类的开关。
4. 唯一能改的做法：在本进程监听/轮询，用
   `NotificationManager.getActiveNotifications()` 拿到那条通知，
   改 `notification.extras` 里的 `Notification.EXTRA_TITLE`，再用同一 id `notify()` 覆盖。
   缺点：库每次重贴（连接建立、SPP 出错、断开等时机）都会覆盖回去，必须跟着重贴，
   属于典型的 hack。
5. 与本次改动叠加后还有额外问题：若本应用自己不再持有通知，用这种方式
   "接管"库的通知，等于把两件事耦在一起，日后排查会非常痛苦。

**已决定放弃**，接受 `SDL: 包名` / `SmartDeviceLink` 这个标题。

## 十二、恢复后的实现（2026-11-22 晚）

### 12.1 为什么最终还是留两条

| 事实 | 来源 |
|---|---|
| SDL 库为 router service 发一条；**每个 SDL app 再为自己的 manager service 发一条** | SDL-0309 提案原文 |
| 「**应用开发者无法影响**这些通知」 | 同上 |
| 官方想加「开关 API」/「通知上加 Stop Now 按钮」的提案 → **Rejected** | 同上（Status: Rejected） |
| 官方的用户侧解法：**长按通知 → 关闭** | 官方 FAQ「SDL Notifications」 |

既然躲不过，去掉自己那条只会白丢前台保护 → 恢复。

### 12.2 通知规格

| 项 | 值 |
|---|---|
| 渠道 | `syncglance` / `IMPORTANCE_LOW` / 无角标 / 无声（落在「静音」分组） |
| 通知 id | `1` |
| 标题 | `西改改的Sync`（取 `R.string.app_name`） |
| 正文 | 见 12.3 状态矩阵 |
| **小图标** | `res/drawable-*/sdl_tray_icon.png`（SDL 六边形线框，从 AAR 复制） |
| **大图标** | **不设** —— 与官方 App 那条截图一致（大图标只有 Router 那条才有） |
| 行为 | `setOngoing(true)` 不可划掉 / `setShowWhen(false)` / `setOnlyAlertOnce(true)` |
| 点击 | 打开 `MainActivity` |
| 关闭时 | `stopForeground(STOP_FOREGROUND_REMOVE)`，**不删渠道** |

> 库的 Router 那条通知保持原样（`SDL: 包名` / 绿色大图标），我们只能改自己这条。

### 12.3 状态矩阵（定稿）

决策优先级**从上往下，命中即止**：

| # | 条件 | 正文 |
|---|---|---|
| 1 | `retryPending`（秒失败等重试） | `Connecting through SDL (Retrying 1/4)` |
| 2 | `DISCONNECTED` 且 `closedOnce` | `Connection closed` |
| 3 | `DISCONNECTED` 且 `routerAlive` | `Waiting for connection (Router listening)` |
| 4 | `DISCONNECTED` 且 `!routerAlive` | `Waiting for connection (Bluetooth not connected)` |
| 5 | `CONNECTING` 且 `managerStarted` | `Connecting through SDL (Waiting for head unit)` |
| 6 | `CONNECTING` 且 `routerAlive` | `Connecting through SDL (Registering)` |
| 7 | `CONNECTING` 且 `!routerAlive` | `Connecting through SDL (Waiting for Router)` |
| 8 | 其余（`NONE/BACKGROUND/LIMITED/FULL`） | `Connected through SDL (HMI: 内容)` |

**已连接的 16 格**（`HMI: 内容`，HMI ∈ FULL/LIMITED/BACKGROUND/NONE，
内容 ∈ `IDLE` / `PLY` / `NAV` / `PLY/NAV`）：

```
Connected through SDL (FULL: IDLE)        Connected through SDL (NONE: IDLE)
Connected through SDL (FULL: PLY)         Connected through SDL (NONE: PLY)
Connected through SDL (FULL: NAV)         Connected through SDL (NONE: NAV)
Connected through SDL (FULL: PLY/NAV)     Connected through SDL (NONE: PLY/NAV)
（LIMITED / BACKGROUND 同理）
```

**几个设计取舍**：

1. `retryPending` **必须最先判** —— 秒失败后 `lifecycle` 已经是 `DISCONNECTED`，
   不特判会错显示成「Waiting for connection」。
2. `(Connecting to Router)` 和 `(Registering)` **合并成一条** —— 区分它们需要
   「传输层是否已绑上 Router」的信号，而 5.x 不对外暴露（`onStart` 要等 RAI 成功）。
3. `head unit` 而不是 `HMI` —— 通知是给用户看的，`HMI`（Human-Machine Interface）
   是车机的**界面子系统**，缩写对外行没意义。
4. `Waiting for connection (...)` **故意不带 SDL** —— 模仿库自己那条的原文，两条措辞一致。
5. 括号用**半角**（正文是英文）。
